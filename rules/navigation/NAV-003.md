## Rule

Navigation that repeats on several pages of a product, such as a top bar, a sidebar or a row of footer links, lists its items in the same relative order on every page, unless the person changed the order themselves.

## Why

People learn a menu once and then reach for an item by where it sits in the list. A screen reader user learns it as a sequence, and a person using magnification learns it by where it is, because they see only part of the screen at a time. When two items swap places from one page to the next, all of them have to start reading the menu again, and some will pick the wrong item. [WCAG 2.2, 3.2.3 Consistent Navigation](https://www.w3.org/TR/WCAG22/#consistent-navigation) requires that navigation repeated across a set of pages keeps the same relative order. "Relative" matters: an item may be added on some pages or left out on others, as long as the items that remain keep their order. The Working Group lists a menu whose links come in a different order on two pages as a failure ([F66](https://www.w3.org/WAI/WCAG22/Techniques/failures/F66)). In WCAG's terms, everything at one URL is one page ([Understanding 3.2.3](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html)). In an app, routes with their own URL are separate pages and the criterion compares them. Views that switch without changing the URL count as one page, so keeping their order is our own advice there.

## Do

- In the invoicing app *Tallowbrook*, the sidebar reads *Dashboard*, *Invoices*, *Clients*, *Reports*, *Settings* on every view. Build it from one shared list, such as `navItems`, rendered by one `AppSidebar` in the root layout, so no page can build its own.
- Filter that one list for items the person may not use; never sort it differently per page. A bookkeeper without access to *Reports* sees *Dashboard*, *Invoices*, *Clients*, *Settings*, which keeps the order.
- An expanded group under *Invoices*, such as *Drafts* and *Overdue*, may appear on some pages. Items inserted that way do not break the order.
- Render the mobile sheet from the same list as the desktop sidebar, so the order holds at every width. Every link must also survive the collapse, as LAY-001 says.
- When the person drags *Clients* to the top of their sidebar, keep their order on every page until they change it again.
- Our own advice: keep a list of recently opened clients in its own labelled group below the main items, rather than sorting the main items by recent use. The main list stays fixed.
- Our own advice: keep the same set of items on every page. When *Reports* has nothing to show yet, keep the item and explain on its page why it is empty, rather than hiding it. The criterion would allow hiding it.
- Our own advice: keep the menu in the same place on screen too. The criterion is about order, not position.
- Buttons that keep their place from page to page are ACT-003b.

## Don't

- Let the dashboard list *Dashboard*, *Invoices*, *Clients* and the settings page list *Clients*, *Dashboard*, *Invoices*, because each page builds its own array.
- Move the current item to the top of the menu, or let a pinned item jump to the front on some pages only.
- Build the mobile sheet from a second, hand-written list that has drifted from the sidebar.

## Exceptions

- **A change the person made.** An order the person set themselves is allowed, and it then holds.
- **A flow without the menu.** A checkout or sign-up flow that drops the product's navigation is a separate set of pages. The rule does not ask it to show the menu.
- **Other language versions.** Each language version of the product is its own set.
- **Position on narrow screens.** Moving the menu from a sidebar into a sheet changes where it is, not its order. The order still holds; LAY-001 covers the rest.
