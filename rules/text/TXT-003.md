## Rule

Let people tell where each link goes or what it opens from its visible text, its accessible name, or its text with the list item, table cell, paragraph or sentence around it; an added name keeps the visible words. A vague phrase with nothing around it naming the destination is not enough.

## Why

Many people meet a link without the page around it. A screen reader user may jump from link to link, or pull up a list of every link on the page. Someone scanning reads the link and little else. If the link only says "More" or "Here", they have to guess, follow it to find out, or give up. Words that name the destination let everyone decide before they go.

This is a requirement. [WCAG 2.2, 2.4.4 Link Purpose (In Context)](https://www.w3.org/TR/WCAG22/#link-purpose-in-context) asks that a link's purpose can be told from its text alone or from its text together with context that software can tie to it: the same sentence, paragraph or list item, the same table cell, or the header of that cell. Words added to the link's accessible name count too. A heading above the link may help people, but on its own it is not the context 2.4.4 counts, so do not lean on it. Context placed somewhere else on the page, such as a side note, does not count.

When you add words to a link's name, [2.5.3 Label in Name](https://www.w3.org/TR/WCAG22/#label-in-name) asks that the visible words stay in the name, so a person using speech control can say what they see. Put the visible words first where you can. This is the same point ACT-001b makes for buttons.

Link text that makes sense with no context at all is our aim, as in [2.4.9 Link Purpose (Link Only)](https://www.w3.org/TR/WCAG22/#link-purpose-link-only). That criterion is Level AAA. We recommend it, but it is not part of this rule's requirement.

## Do

- In a list of invoices, each row links its number: *Invoice 2291*, *Invoice 2292*. The link text says where it goes.
- In a list of team members, each list item reads "Dana Ruiz, editor" and ends with the link *Profile*. The list item says whose profile it opens. Better still: *Dana Ruiz's profile*.
- In a table of monthly reports, each row has a link *Download* in the same cell as the month and the file type, *March, CSV*, or under a column header the cell is tied to in code (TBL-001). Better still: *Download March report (CSV)*.
- A card on a status page shows the link *Details* and gives it the name "Details: outage in the Frankfurt region". The visible word comes first in the name.
- In a sentence like "Your trial ends on 3 December. *See plans and prices* to keep your projects.", the link names the page it opens.
- Treat *More*, *Here*, *Click here*, *Read more*, *Learn more*, *Details*, *View* and *Continue* as link texts that always need context in the same sentence, list item or cell, or added words in the name. The list is our own and is not complete.
- Write the destination first and any generic lead-in after it, so a person scanning a list of links reads the telling words first.
- In shadcn, keep the words that name the destination inside the link element itself. When a short visible word must stay, add the rest with a visually hidden `span` inside the link, or with `aria-labelledby` pointing to the text that names the destination.
- A link that is only an image or an icon gets a text alternative that names where it goes, such as "Company home page" for a logo link.

## Don't

- End every card in a grid of recipes with the same link *Continue* when nothing in the card's own text, list item or cell says which recipe it opens.
- Rely on a heading above a group of *View* links as the only clue to where each one goes.
- Give a link that shows *Details* the `aria-label` "Outage report for Frankfurt". The word on screen is no longer in the name, so a speech command for it does nothing.
- Rely on `aria-describedby` alone for the context. The usual ways put the words in the link's name, with `aria-labelledby`, `aria-label` or visually hidden text, and a description is often not read when someone browses a list of links. Prefer visible context in the same sentence, list item or cell, or words in the name.
- Leave a link that holds only an icon with no name, so a screen reader announces just "link".
- Show the context only visually, for example by position next to a photo, with nothing in the text or the name.

## Exceptions

- **Purpose unclear to every reader.** 2.4.4 does not apply when the purpose of a link would be unclear to any reader, sighted or not, from the link and everything the page shows with it. Our choice, beyond the requirement: we do not use this exception for a link we could describe, and we describe it instead.

This rule is about anything that is a link in code. Labels on buttons follow ACT-001a and ACT-001b. A link styled as a button is still a link and follows this rule; which of the two to build is ACT-009a and ACT-009b, and the role itself ACT-009. A link whose meaning comes from the sentence before it meets this rule only when that sentence shares the paragraph, table cell or list item with the link, or is tied to it in code. The sign-in link in TXT-001a meets it when the sentence and the link sit together in one message. Opening a new tab, naming file types and marking links to other sites are left to separate rules. How a link in running text looks is VIS-003b.
