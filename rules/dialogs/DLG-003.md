## Rule

In a dialog that asks the person to confirm a destructive action, label the button that performs it with a verb that names that action, never "OK", "Yes" or another word that does not say what will happen, and always include a button labelled Cancel that is enabled and closes the dialog with nothing changed.

## Why

A destructive action deletes, overwrites or takes away something the person cannot easily get back. A dialog that checks before such a step only helps if each button says plainly what it will do. "OK" and "Yes" make the person read the question again and work out what the answer means, and people in a hurry skip that step. A button that reads *Delete project* states the result on its face, and a screen reader user hears the same words. A Cancel button that always works is the other half: there has to be a plain, safe way back, with no doubt about whether leaving will run the action. No WCAG criterion asks for these labels. They help meet [WCAG 2.2, 2.4.6 Headings and Labels](https://www.w3.org/TR/WCAG22/#headings-and-labels), and a visible label that is also the button's accessible name supports [2.5.3 Label in Name](https://www.w3.org/TR/WCAG22/#label-in-name) and [4.1.2 Name, Role, Value](https://www.w3.org/TR/WCAG22/#name-role-value). A chance to check before a final step is one of the safeguards that [3.3.4 Error Prevention (Legal, Financial, Data)](https://www.w3.org/TR/WCAG22/#error-prevention-legal-financial-data) accepts where it applies. Being able to undo the action is another, and it is often kinder than asking.

## Do

- A dialog titled "Delete the project Autumn 2026?" has the buttons *Cancel* and *Delete project*.
- Use the same verb in the title and on the button: "Remove Jordan Lee from the team?" with *Remove*. A short verb is enough when the title says what it acts on. Adding the object, as in *Remove member*, is clearer still.
- Name the real result: *Revoke access*, *Reset settings*, *Delete all receipts*.
- Label the safe button *Cancel* in every such dialog, so people always find the way back under the same word, and let it close the dialog with nothing changed. Escape does the same, as DLG-001 says.
- If *Delete project* stays unavailable until the person types the project's name, keep *Cancel* usable the whole time, and show the text before the button that ACT-005 asks for.
- Use the visible text as the button's accessible name, so a voice control user can say "Delete project" and a screen reader reads the same words.

## Don't

- Ask "Do you want to delete the project?" with *OK* and *Cancel*, or with *Yes* and *No*.
- Put *Confirm* or *Continue* on the button that deletes. Neither word says what will be lost.
- Offer only *Delete* and a close icon, with no *Cancel*.
- Grey out *Cancel* until something else is done, or let it run any part of the action.
- Give *Delete project* an `aria-label` such as "Confirm" that differs from its visible text.

## Exceptions

- **Actions that can be undone.** Archiving a project that stays one click away under *Archive* needs no dialog. Show a message with *Undo* instead. DST-001b decides when a dialog is needed at all, and DST-001a how *Undo* is offered. When no dialog is shown, this rule does not apply.
- **While the action runs.** After the person has pressed the destructive button and the dialog shows progress, such as "Deleting …", STA-005a covers what Cancel, Escape and the close icon do. Its own choice is that Cancel stops the request only when it can truly be withdrawn, and that otherwise all three are unavailable until the reply.
- **Focus and style.** Where focus lands when the dialog opens is covered by DLG-004, and how the destructive button looks by DLG-005.
