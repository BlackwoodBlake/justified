## Rule

Everything a person can do with a pointer can also be done with the keyboard alone, unless the task depends on the path of the movement; and whenever an element has keyboard focus, a visible indicator marks it for as long as it has focus.

## Why

Many people never touch a mouse or a touch screen. Some cannot see a pointer, some cannot hold one steady, and some move faster with keys. For them, a task that needs a pointer is a task they cannot finish, and a page that hides focus leaves them guessing where the next key press will land. [WCAG 2.2, 2.1.1 Keyboard](https://www.w3.org/TR/WCAG22/#keyboard) requires that all functionality works from a keyboard, either through the same control or through a comparable keyboard route that reaches the same result, and [2.4.7 Focus Visible](https://www.w3.org/TR/WCAG22/#focus-visible) requires that keyboard focus can be seen. Neither sets a size or a shape for the indicator. When we style the indicator ourselves, [1.4.11 Non-text Contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast) also applies: it shows a state, so the part people need to see in order to find focus needs at least 3:1 against the colours next to it. Those are the colours it actually touches, so where you draw the ring decides what it is measured against. An indicator left exactly as the browser draws it is outside that figure but must still be visible. [2.4.13 Focus Appearance](https://www.w3.org/TR/WCAG22/#focus-appearance) sets further thresholds, but it is Level AAA, so it is a further step you may take, not a requirement of this rule.

## Do

- Build actions from real `<button>`, `<a href>` and form elements. They take focus and respond to keys without extra code. In the shadcn adapter, `Button`, `Checkbox`, `RadioGroupItem`, `Switch` and the field controls already do this.
- Give a sortable list *My favourites* a keyboard route next to the drag handle: a menu on each row with *Move up* and *Move down*, or arrow keys while the row is picked up. Keep a click or tap way that needs no dragging too, as ACT-007a requires; what a screen reader hears during the move is ACT-007b.
- Let a price slider *Price, £0–£5,000* move with the arrow keys, and let Home and End jump to its ends.
- When a row in *Upcoming bookings* shows *Change* and *Cancel booking* on hover, show them on keyboard focus as well. In a table row, TBL-003 covers this.
- Offer a keyboard shortcut such as Ctrl+Shift+N for *New note* as an extra, beside a button that does the same thing.
- Keep the indicator on for as long as the element has focus. Showing it only for keyboard focus, as `:focus-visible` does, is fine.
- Keep the visible part of an indicator we style ourselves at 3:1 or more against the colours next to it, in both themes. We measure in both themes, as VIS-001 explains. Our `focusRing` draws a 2px ring outside the control with a 2px gap in the page colour, and our contrast test checks the ring against the page, card, muted and accent surfaces in both themes.
- Make the indicator survive forced-colours mode (Windows high contrast). That mode drops box shadows, so a shadow ring alone disappears. Our `focusRing` keeps `outline-none` on the base state and adds `focus-visible:outline-hidden`, a transparent outline that forced-colours mode draws in a system colour, so an outline appears there on keyboard focus. This is our own technical point.
- Give every focusable thing an indicator: links, switches, radio buttons, a scrollable *Terms* box and a card that acts as one big link.

## Don't

- Put a click handler on a `<div>` that looks like a button, such as *Show more trips*, and give it no focus and no key handling.
- Let a file upload *Upload receipt* work only by dropping files on a drop zone, with no button that opens the file picker. It fails ACT-007a as well.
- Set `outline: none` on all controls and add nothing in its place, so Tab moves through *Search tickets* without any visible sign.
- Show focus on *Add passenger* only by turning its background a shade lighter. It is easy to miss and may rely on colour alone; use a ring or an outline.
- Let the ring fade out a second after a control gets focus.
- Move focus away by script as soon as an element receives it.
- Make a key held down for two seconds, or a fast double press, the only way to confirm *Confirm payment*.
- Treat a mode that steers the mouse pointer with the arrow keys as keyboard support.

## Exceptions

- **Path-based tasks.** When the result is the path itself, such as tracing a running route by hand on a map in *Draw your route*, that tracing is exempt. The controls around it, such as *Undo*, *Clear* and *Save route*, are not, and a way to enter the route stop by stop is still welcome.
- **Disabled controls.** A control that is off need not take focus; ACT-005 relies on this.
- **Neighbouring rules.** Getting out of a dialog by keyboard is in DLG-001, focus into, inside and out of a modal dialog is in DLG-006 and DLG-007, the order focus moves in is in LAY-002, and focus hidden by sticky bars or other layers is in KBD-002. The way without dragging is ACT-007a, sortable table headers TBL-002 and row actions TBL-003. This rule does not repeat them.
