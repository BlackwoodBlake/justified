## Rule

Everything that does something when pressed, including a clickable card, row or list item, changes its look while it is pressed and, where the pointer can hover, while the pointer is over it. A control that is off shows neither change.

## Why

A press that changes nothing on screen leaves people unsure whether it was taken, so they press again, or give up on a control that works. A change under the pointer tells them, before they click, that this is the thing that will respond, and that the card they are pointing at is one target and not three. The same looks on a control that is off promise an action that is not there. No WCAG criterion asks for hover or pressed looks. The explanation of [WCAG 2.2, 1.4.11 Non-text Contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast) treats an author's hover look as an extra, since the pointer itself already shows where it is, so this rule rests on the judges. That the Apple stance also holds on the web is our own reading. A hover look confirms what the element at rest should already show: that it can be used. It does not replace that.

## Do

- In a project dashboard, each project is a `Card` with a link to the project stretched over it (`after:absolute after:inset-0` on the link, `relative` on the card). The card gets `hover:bg-accent hover:text-accent-foreground` and a pressed look such as `active:shadow-inner`, and keeps its `border` at rest so it looks like one target before anyone points at it. Which fill to use is VIS-002; text on the new fill follows VIS-001.
- Give every pressable element an `active:` style as well as a `hover:` one. Tailwind v4 applies `hover:` only on devices that can hover, so on a phone a tap shows nothing unless there is an `active:` style, which applies on touch too.
- On a phone, a tile in *Today's tasks* shows its pressed look as soon as the finger lands on it. It has no hover look there, and needs none. Check the press on a real phone: a browser may hold the pressed look back for a moment inside an area that scrolls.
- On a file card, the icon buttons *Download*, *Share* and *Rename* each have a hover fill and a pressed look. Their names in code are ACT-001b, and their size is ACT-006.
- Build menus and command lists from shadcn's `DropdownMenu`, `Select` or `Command`, which light the item under the pointer and the keyboard. If you must build a list by hand, give each item the same highlight.
- Keep a control that is off still. Tailwind's `disabled:` variant matches only the native attribute, so a menu item or button with `aria-disabled="true"` keeps its `hover:` and `active:` classes. Scope them with `not-aria-disabled:hover:bg-accent` and `not-aria-disabled:active:…`. Avoid `pointer-events-none` for this: it also blocks a tooltip that says why the control is off.
- Our own choice: show the pressed look at once on the press, with no delay. Any motion in the change follows VIS-006.
- Our own advice: make a pressable element look usable at rest, with a border, a link style, a chevron or a button shape, so nobody has to sweep the pointer over the page to find out.

## Don't

- Put `onClick` on a `Card` or a `div` row and give it only `cursor-pointer`. The cursor is not a change of the element, and a touch screen has no cursor at all.
- Strip a ghost `Button` of its hover with `className="hover:bg-transparent"` and put nothing in its place.
- Map a list of plain `div` items in place of a `DropdownMenu`, so the item under the pointer looks like every other item.
- Give a static summary `Card` or a decorative picture `hover:shadow-lg`. It invites a click that does nothing. This is our own advice; the rule itself only keeps the looks off a control that is off.
- Let a menu item marked `aria-disabled="true"` light up on hover and darken on press like the items that work.

## Exceptions

- **Row highlight as a reading aid.** A table row that lights up under the pointer to help the eye follow it, as shadcn's `TableRow` does with `hover:bg-muted/50`, is fine, and so is a row whose actions appear on hover, which TBL-003 covers.
- **Whole containers.** A bar, a dialog, a sheet or a panel as a whole takes no hover or pressed look. The controls inside it do.
- **Controls the browser draws.** A native control left with the browser's own styling keeps the browser's own response.
- **Touch only.** Where the device has no pointer that can hover, only the pressed look applies.
- **Neighbouring rules.** The focus indicator and keyboard reach are KBD-001. Content or actions that appear on hover are TXT-002a, TXT-002b and TBL-003. The contrast of a control's edge and marks while it is hovered or pressed is VIS-004. Which token draws the change is VIS-002. A selected or on state kept visible under hover and press is VIS-008b. A control that is off is off in code too, as VIS-008a says. What a button shows after the press while its action runs is STA-005a.
